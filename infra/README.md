# Infra: инфраструктура формы авторизации

Второй этапчик: улучшенная версия учебного проекта `native` (форма авторизации на HTML/CSS/JS). Здесь добавили менеджер пакетов, фиксацию версии ноды, typescript со строгой проверкой типов, сборщик с dev-сервером, линтер, форматтер и unit-тесты.

Исходный проект `native` не менялся. Все доработки находятся в папке `infra`.

Основная работа пушилась в ветку `features`, потому что я решил продолжить традицию с `native`.

Пропустил пару саминаров в конце прошлого модуля из-за смерти процессора, бтв. Сейчас всё норм, я это к тому, что не все решения принятые здесь могут совпадать с ходом работы на занятиях.

## Быстрый старт

Проект рассчитан в первую очередь на unix-системы. Запускался и проверялся в Git bash на винде, для интереса сравнивал с терминалом на линуксе.

Требования:

- Git Bash или любой unix-терминал
- [fnm](https://github.com/Schniz/fnm) (подойдёт и nvm): нужная версия Node.js указана в файле `.nvmrc`
- Corepack: идёт вместе с Node.js (до версии 24 включительно); для Node.js 25 и новее его нужно поставить отдельно: `npm install -g corepack`

```bash
git clone git@github.com:dnslm/webdev-26.git
# https: https://github.com/dnslm/webdev-26.git

cd webdev-26/infra
fnm install         # если вдруг нету
fnm use             # переключает Node.js на версию из .nvmrc
corepack enable     # подключает версию Yarn из поля packageManager
yarn install        # устанавливает зависимости
yarn serve          # запускает dev-сервер
```

После запуска страница доступна по адресу <http://127.0.0.1:5173/>.

Если в системе уже стоит глобальный Yarn 1.x, то без `corepack enable` команда `yarn` запустит именно его и выдаст ошибку про поле `packageManager`.

Чтобы версия Node.js переключалась автоматически при входе в папку проекта, добавьте в `~/.bashrc`:

```bash
eval "$(fnm env --use-on-cd --shell bash)"
```

## О приложении

Страница входа: кнопки входа через соцсети (Google и Apple, без логики), поля email и пароля, чекбокс Запомнить пароль? и кнопка Войти.

- **Валидация.** Email проверяется по формату, пароль должен содержать минимум 8 символов, хотя бы одну букву и одну цифру. Проверка срабатывает при уходе с поля и при отправке формы.
- **Проверка входа.** Верная пара email/пароль захардкожена в `src/auth.ts` (демо-данные: `test@email.com` / `abobaBebra1487`). Вход сопровождается состоянием загрузки на кнопке и сообщениями пользователю.
- **Сохранение данных.** Если чекбокс отмечен, после успешного входа пара сохраняется в `localStorage` и подставляется в форму при следующей загрузке страницы.
- **Эффекты.** Конфетти после успешного входа. Пасхалка: если набрать на странице (не в поле ввода) слово `bebra`, включается снегопад, повторный ввод выключает его. Эффекты отключаются, если у пользователя включён режим уменьшения анимации.

## 1. Менеджер пакетов

**Что сделано:** проект инициализирован через `yarn init`, используется **Yarn 4**. Точная версия закреплена в поле `packageManager` файла `package.json` (ещё продублирована в `engines.yarn` (`package.json`)) и подключается через Corepack. Настройки Yarn лежат в `.yarnrc.yml`: используется режим установки `nodeLinker: node-modules`.

**❓ Почему выбран Yarn:**

- **Одинаковая версия у всех** Поле `packageManager` вместе с Corepack гарантирует, что у каждого, кто клонирует репозиторий, будет одна и та же версия Yarn, а `yarn.lock` фиксирует точные версии всех зависимостей. Установка получается воспроизводимой.
- **Удобный запуск скриптов** Команды вида `yarn serve`, `yarn lint`, `yarn test` короче и единообразны, а Yarn умеет запускать бинарники пакетов без дополнительной настройки.
- **Быстрая установка и общий кэш** Пакеты кэшируются глобально в профиле пользователя, а не в репозитории, поэтому повторные установки быстрые и папка проекта остаётся лёгкой.
- **Почему не npm и не pnpm** npm тоже подошёл бы (он идёт с Node.js), но у Yarn из коробки жёстче закрепляется версия самого менеджера. pnpm экономит место на диске, но для проекта с десятком зависимостей это не критично.

**Принятое решение: Plug'n'Play отключён.** По умолчанию Yarn 4 устанавливает зависимости в режиме Plug'n'Play (без папки `node_modules`). Для Vite 8 заявлена несовместимость с этим режимом, поэтому выбран классический `nodeLinker: node-modules`. Заодно инструменты (ESLint, Vitest, редактор) работают с ним без дополнительной настройки.

## 2. Фиксация версии Node.js

**Что сделано:** версия Node.js v24 зафиксирована в файле `.nvmrc`, для переключения используется **fnm**. Ту же версию задаёт поле `engines` (>=24 <25) в `package.json`. Команда `fnm use` переключает Node.js на нужную версию.

**Почему именно эта версия:** выбрана актуальная LTS-версия: она получает обновления безопасности, а сборщик Vite 8 требует Node.js не ниже 20.19 или 22.12, так что любая современная LTS подходит. Закрепление версии нужно, чтобы проект одинаково работал на разных машинах и в разное время.

## 3. TypeScript

**Что сделано:** весь код из `script.js` переведён в TypeScript (`script.ts`), логика разнесена по модулям. При переходе компилятор нашёл около 60 ошибок в одном файле. Основные:

- обращения к DOM: `getElementById` возвращает `HTMLElement | null`, а у обычного элемента нет `.value`. Решение: функция `getElement`, которая проверяет тип через `instanceof` и сразу выбрасывает понятную ошибку, если элемента нет;
- параметры функций без типов;
- `event.target` может быть `null` и необязательно является элементом;
- обращение к элементу массива, который может оказаться `undefined`;
- обращения к функциям по старым именам после переименования. В обычном JavaScript это привело бы к ошибке уже при работе страницы.

Также данные из `localStorage` разбираются как `unknown` и проверяются функцией-защитником типа: пользователь может вручную изменить значение в DevTools.

**Описание типов данных** (файл `src/types.ts`):

```ts
// тип сообщения для пользователя: от него зависит цвет текста
export type MessageType = "error" | "success";

// пара логин/пароль: её вводят в форму и сохраняют в localStorage
export interface UserData {
    email: string;
    password: string;
}
```

Остальные функции типизированы явно: например, `isValidEmail(value: string): boolean`, `setFieldState(input: HTMLInputElement, isValid: boolean): void`.

**Проверка типов:** `yarn typecheck` (`tsc --noEmit`).

**Версия TypeScript.** Используется TypeScript 6.x, а не 7.0. Седьмая версия представляет собой нативный компилятор и на момент выполнения работы не имеет программного API, которым пользуется typescript-eslint. Поэтому для работы линтера с проверкой по типам нужна шестая версия.

**❓ Почему выбрана такая конфигурация `tsconfig.json`:**

| Настройка | Зачем |
|---|---|
| `strict: true` | включает весь набор строгих проверок (`strictNullChecks`, `noImplicitAny` и тд): основа строгой типизации |
| `noUncheckedIndexedAccess` | элемент массива считается возможно `undefined`; это предотвращает ошибки обращения за границы массива |
| `exactOptionalPropertyTypes` | необязательное свойство нельзя явно присвоить `undefined`, различие между "нет свойства" и "свойство равно undefined" остается |
| `noImplicitReturns`, `noImplicitOverride`, `noFallthroughCasesInSwitch` | ловят забытые `return`, неявное переопределение методов и проваливание между `case` |
| `noUnusedLocals`, `noUnusedParameters` | неиспользуемый код считается ошибкой |
| `noPropertyAccessFromIndexSignature` | поля словарей обязательно читаются через `[]`, чтобы опечатка в имени свойства не прошла незамеченной |
| `noUncheckedSideEffectImports` | проверяет, что импорты указывают на существующие файлы |
| `verbatimModuleSyntax`, `isolatedModules` | импорты типов пишутся явно (`import type`), код безопасно обрабатывается сборщиком по одному файлу |
| `module: esnext`, `moduleResolution: bundler` | модули разрешает сборщик Vite, а не Node.js, поэтому не нужны расширения в путях импорта |
| `target: ES2022`, `lib: [ES2022, DOM, DOM.Iterable]` | современный JavaScript и типы браузерных API (`document`, `localStorage`) |
| `noEmit: true` | компилятор только проверяет типы, а код собирает Vite |
| `include: [src, vite.config.ts]` | проверяются исходники, тесты и конфиг сборщика |

Выбран максимально строгий набор настроек: новый код проще писать правильно сразу, чем исправлять потом. Предустановленные пресеты вроде `@tsconfig/strictest` не использовались, потому что полный список опций полезен и для понимания, и для объяснения.

## 4. Сборщик и dev-сервер

**Команды:**

- `yarn serve` запускает dev-сервер Vite. Исходники отдаются на лету, изменения в коде и стилях применяются в браузере мгновенно, без перезагрузки страницы. Адрес: <http://127.0.0.1:5173/>.
- `yarn build` сначала проверяет типы (`tsc --noEmit`), затем собирает production-версию в папку `dist/`: TypeScript компилируется в JavaScript, код и стили минифицируются, к именам файлов добавляется хэш содержимого, а `index.html` обновляется под новые файлы.
- `yarn preview` запускает локальный сервер для готовой сборки из `dist/`, чтобы проверить итоговый результат (порт 4173).

**Настройки** (`vite.config.ts`): корнем проекта указана папка `src` (там лежат `index.html`, стили и картинки), результат сборки пишется в `../dist` с очисткой папки перед каждой сборкой. Для dev-сервера задан адрес `127.0.0.1`: с `localhost` Firefox на винде у меня не открывал страницу (вроде как из-за расхождения IPv4 и IPv6 ??).

**❓ Почему выбран Vite:**

- **Почти без настройки** TypeScript, CSS, картинки и HTML обрабатываются из коробки. Для сравнения, у webpack пришлось бы настраивать загрузчики и отдельный dev-сервер.
- **Быстрый dev-сервер** Vite не собирает весь проект перед запуском, а отдаёт файлы браузеру как ES-модули, поэтому старт и обновление страницы довольно быстрые.
- **Современная сборка** Восьмая версия собирает production-версию на Rust-сборщике Rolldown, а результат получается небольшим, в проекте весь код вместе занимает несколько килобайт.
- **Единая экосистема** Тесты (Vitest, см. далее) используют тот же `vite.config.ts` и ту же обработку кода, что и сборка.
- **Почему не альтернативы** webpack избыточен для проекта такого размера. Parcel удобен, но менее распространён, не было бы такой интеграции с Vitest. esbuild сам по себе быстрый, но готового dev-сервера с обновлением страницы из коробки не даёт.

## 5. Линтер

**Что сделано:** установлены ESLint и `typescript-eslint`, настройки лежат в `eslint.config.mjs` (современный плоский формат конфигурации). Подключены:

- `eslint.configs.recommended`: базовые правила для джаваскрипт;
- `tseslint.configs.strictTypeChecked` и `tseslint.configs.stylisticTypeChecked`: самые строгие готовые наборы typescript-eslint, правила которых используют информацию о типах (`projectService: true`);
- для обычных `.js`/`.mjs`-файлов (например, самого конфига) проверка по типам отключена;
- `eslint-config-prettier` последним: он отключает правила, которые конфликтуют с форматированием Prettier;
- из проверки исключены `dist`, `.yarn` и служебные файлы Yarn.

**Команды:**

- `yarn lint` проверяет код;
- `yarn lint:fix`: проверяет код и по возможности исправляет найденные ошибки.

**❓ Почему выбрана такая конфигурация:**

- **Готовый пресет** Набор правил от авторов typescript-eslint поддерживается и обновляется комьюнити, поэтому отдельный подбор правил не нужен.
- **Строгий набор.** `strictTypeChecked` согласуется со строгим `tsconfig.json`: проверки типов компилятором и правила линтера дополняют друг друга.
- **Правила с информацией о типах** находят ошибки, которые обычный линтер не видит. Личный пример: правило `restrict-plus-operands` нашло 7 мест, где число неявно складывалось со строкой (`Math.random() * 100 + "vw"`). Результат такого сложения легко перепутать, поэтому теперь используется небольшая функция с явным преобразованием.
- **`stylisticTypeChecked`** следит за единообразным стилем кода (не за форматированием, этим занимается Prettier).
- **`eslint-config-prettier`** разделяет ответственность: линтер ищет ошибки в логике, форматтер отвечает только за внешний вид.

## 6. Форматтер

**Что сделано:** установлен Prettier (версия закреплена точно, так как разные версии могут форматировать код слегка по-разному) и `eslint-config-prettier`. Настройки лежат в `.prettierrc.yaml`, список исключений - в `.prettierignore` (`dist`, `.yarn`). Prettier умеет форматировать TypeScript, HTML, CSS, JSON и Markdown без доп плагинов.

**Команды:**

- `yarn format` (`prettier --write .`)  автоматически исправляет форматирование;
- `yarn format:check` (`prettier --check .`) только проверяет, ничего не меняя. завершается с ошибкой, если какой-то файл отформатирован неверно.
- `git diff --stat` ревьюит изменения `yarn format`

**❓ Почему выбрана такая конфигурация:**

| Опция | Значение | Почему |
|---|---|---|
| `printWidth` | 100 | в проекте длинные комментарии и строки, 80 символов (значение по умолчанию) приводит к лишним переносам |
| `tabWidth` | 4 | отступ в 4 пробела, как в уже написанном коде (по умолчанию у Prettier 2) |
| `semi` | `true` | точка с запятой в конце выражений |
| `singleQuote` | `false` | двойные кавычки, как в остальном коде |
| `trailingComma` | `all` | запятая после последнего элемента списка: при добавлении элемента в git меняется только одна строка |
| `arrowParens` | `always` | скобки у параметра стрелочной функции всегда: `(x) => x` |
| `endOfLine` | `lf` | одинаковые окончания строк на Unix и Windows (проект должен запускаться на Unix) |

Значения подобраны под уже существующий стиль кода, чтобы первое форматирование изменило как можно меньше строк. Настройки `.editorconfig` согласованы с Prettier. Отдельный форматтер нужен, потому что линтер проверяет качество кода, но не должен спорить с командой о пробелах и скобках.

## 7. Тесты

**Что сделано:** установлены **Vitest** и **jsdom**. Настройки находятся в `vite.config.ts` в секции `test` (окружение `jsdom`). Тесты лежат рядом с кодом в `src/` в файлах типа `*.test.ts`, которые Vitest находит автоматически. В общей сложности - 35 тестов в 3 файлах.

Чтобы код можно было тестировать, логика вынесена из `script.ts` в отдельные модули: до этого `script.ts` при загрузке сразу обращался к DOM и навешивал обработчики, и импортировать его в тесте нельзя. Теперь `script.ts` отвечает только за связь с DOM, а проверяемая логика находится в `validation.ts`, `storage.ts` и `auth.ts`.

**Что покрыто тестами:**

| Файл | Что проверяется |
|---|---|
| `validation.test.ts` | корректные и некорректные email и пароли, граница в 7 и 8 символов, кириллические символы |
| `storage.test.ts` | сохранение и чтение пары, пустое хранилище, удаление данных, повреждённый JSON, данные неверной формы |
| `auth.test.ts` | верная пара, неверный пароль, неверный email, пустые поля, перепутанные местами поля |

Приёмы: `it.each` прогоняет один тест по таблице входных данных, а `beforeEach` очищает `localStorage` перед каждым тестом, чтобы тесты не влияли друг на друга.

**Команды:** `yarn test` (один запуск) и `yarn test:watch` (повторный запуск при каждом изменении файла).

**❓ Почему выбран этот фреймворк и такая конфигурация:**

- **Vitest, а не Jest.** Vitest использует тот же `vite.config.ts`, что и сборка, поэтому TypeScript и ES-модули работают сразу. Для Jest пришлось бы отдельно настраивать преобразование TypeScript и поддержку ES-модулей. API у Vitest совместим с Jest (`describe`, `it`, `expect`), поэтому дополнительных знаний особо не требуется.
- **Быстрый режим наблюдения.** Тесты перезапускаются при изменении файлов и выполняются очень быстро.
- **Версия.** Vitest актуальной ветки поддерживает Vite 8, который используется в проекте.
- **Окружение `jsdom`.** Тестам хранилища нужен `localStorage`, которого нет в чистом Node.js. jsdom - наиболее полная и распространённая имитация браузерного окружения. Окружение задано один раз для всех тестов, это проще, чем настраивать каждый файл отдельно.
- **Явные импорты из `vitest`** (`import { describe, it, expect } from "vitest"`) вместо глобальных функций: не нужно подключать глобальные типы, а `tsconfig.json` остаётся чистым.
- **Почему не встроенный `node:test`.** У него нет готового окружения для браузерных API и меньше возможностей для таблиц тестовых данных.

## Ограничения

- Пароль хранится в `localStorage` в открытом виде только для демонстрации (всё так же, как и в native, дополнительно пояснял в соответствующем README)
- Проверка логина и пароля захардкожена на клиенте и защиты не обеспечивает.
- Кнопки входа через Google и Apple пока являются заготовками без логики.
- Тесты покрывают чистую логику (валидацию, хранилище, проверку данных). Код, работающий с DOM (`script.ts`), автоматическими тестами не покрыт.
