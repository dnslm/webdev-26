# Framework: форма авторизации на React

Третий этап: тот же интерфейс, что в `native` и `infra`, но на реакте

Форму поделил на переиспользуемые на компоненты, состояние вынес в Zustand, логику проверок и работы с данными оставил отдельными модулями, а тесты разложил рядом с кодом. Ручной DOM из `infra` тут больше не нужен, React сам решает, когда что перерисовать.

## Быстрый старт

Проект рассчитан в первую очередь на unix-системы. Я запускал через Git bash на винде, на линуксе в этот раз не проверяял но надеюсь будет без сюрпризов везде.

Что нужно:

- Git bash или любой нормальный терминал
- [fnm](https://github.com/Schniz/fnm) или nvm: версия Node.js лежит в `.nvmrc`
- Corepack: идёт вместе с Node.js до 24 включительно, для 25 и новее ставится отдельно

```bash
git clone git@github.com:dnslm/webdev-26.git
# https: https://github.com/dnslm/webdev-26.git

cd webdev-26/framework
fnm install
fnm use
corepack enable
yarn install
yarn dev
```

После запуска страница открывается на <http://127.0.0.1:5173/>.

Если глобально стоит Yarn 1.x, без `corepack enable` запустится именно он и ругнётся на поле `packageManager`. Это не баг проекта, это особенность Corepack.

## Что изменилось по сравнению с infra

| Что                  | infra                        | framework                                         |
| -------------------- | ---------------------------- | ------------------------------------------------- |
| Интерфейс            | TypeScript и ручной DOM      | React-компоненты и TSX                            |
| Стили                | один глобальный CSS-файл     | CSS Modules рядом с компонентами                  |

| Эффекты              | создание элементов через DOM | компоненты `Confetti` и `Snow`                    |
| Тесты                | чистая логика                | компоненты, хуки, стор и логика                   |

Логику проверок, работы с `localStorage` и имитацию входа не выкидывал. Она переехала в `src/lib` и `src/store`, чтобы ею могли пользоваться компоненты и тесты.

## О приложении

Страница входа: шапка с логотипом, карточка с кнопками Google и Apple, форма с email и паролем, чекбокс "Запомнить пароль?", кнопка "Войти" и подвал с бегущей строкой (дурацкая, но убирать не захотел всё ещё).

Что работает:

- **Валидация.** Email проверяется по формату, пароль должен быть не короче 8 символов, содержать хотя бы одну букву и одну цифру. Проверка срабатывает при уходе с поля и при отправке формы.
- **Проверка входа.** Верная пара захардкожена в `src/lib/auth.ts`. Пока идёт запрос, кнопка заблокирована и показывает состояние загрузки.
- **Сообщения.** Под формой есть `aria-live`-блок: ошибка формата, неверная пара, успешный вход, восстановленные данные и пасхалка.
- **Сохранение пары.** Если чекбокс отмечен, после успешного входа пара попадает в `localStorage`. При следующей загрузке поля заполняются, чекбокс отмечен, показывается сообщение "Данные восстановлены".
- **Конфетти.** Появляется после успешного входа. Кусочки летят в тех же диапазонах, что в native: случайная позиция, случайный цвет, падение от 1,5 до 3 секунд, задержка до 0,3 секунды.
- **Снег.** Наберите `bebra` на странице, вне поля ввода, и включится снегопад. Повторный ввод выключает его.
- **Уменьшенные анимации.** Если в системе включён `prefers-reduced-motion: reduce`, конфетти и снег не показываются, бегущая строка не анимируется.

## Как это устроено

1. `main.tsx` монтирует `App` в `StrictMode`.
2. `App` читает статус входа из `authStore` и состояние снега из `effectsStore`, подключает `useSecretCode` и решает, какие эффекты показывать.
3. `LoginCard` собирает `SocialLogin` и `AuthForm`.
4. `AuthForm` держит поля через `useField`, локально хранит чекбокс и ошибку формата, а при отправке вызывает `login` из стора.
5. `authStore` ставит `loading`, ждёт `requestLogin`, затем пишет `success` или `error`. В `localStorage` через `persist` попадает только сохранённая пара, без статуса и пользователя.
6. `effectsStore` переключает снег и ставит сообщение-пасхалку. `useSecretCode` слушает клавиши по `event.code`, поэтому раскладка не важна.
7. `Confetti` появляется при статусе `success`, `Snow` при включённом снеге. Оба компонента проверяют `useReducedMotion` и уважают системную настройку.

## Доступность

Многое перенесено из `native`, но теперь это разложено по компонентам:

- у полей есть настоящие `<label>`, скрытые визуально, а не только `placeholder`;
- обязательные поля помечены `required` и `aria-required`;
- ошибка поля передаётся через `aria-invalid`, а не только цветом;
- сообщение под формой живёт в блоке с `aria-live="polite"`;
- кнопка входа во время запроса получает `aria-busy` и `disabled`;
- декоративные иконки имеют пустой `alt`, у логотипа есть `alt` и подпись у ссылки;
- бегущая строка читается скринридером один раз, остальные копии скрыты через `aria-hidden`;
- у страницы есть один `h1`, визуально скрытый;
- конфетти и снег тоже `aria-hidden`, чтобы скринридер не читал сотни пустых `span`;
- все интерактивные элементы нативные: `button`, `input`, `a`, поэтому клавиатура и Tab работают без костылей.

## 1. React и инфраструктурааааААААА

**Что стоит:**

- React 19.3.1 и React DOM 19.3.1;
- Vite 8.3.6 и `@vitejs/plugin-react` 6.1.2;
- TypeScript 6.0.3 со строгими настройками;
- ESLint 10, `typescript-eslint` 8, плагины `react-hooks` и `react-refresh`;
- Prettier 3.10.1;
- Node.js 24 в `.nvmrc` и `engines.node`;
- Yarn 4.18.1 в `packageManager` и `engines.yarn`.

оооххххх

**Почему React.** По заданию третьего этапа нужен именно он. Версия актуальная, хуки и `useSyncExternalStore` закрывают всё, что нужно для формы и эффектов.

**Почему Vite, а не CRA или Next.** CRA уже не стоит брать, Next для одной страницы с формой явно лишний. Vite у меня уже был в `infra`, он быстро стартует, нормально собирает TSX и CSS Modules, а Vitest использует тот же `vite.config.ts`. Меньше конфигов, меньше мест, где что-то может разъехаться.

**Почему TypeScript-конфиг разбит на части.** `tsconfig.app.json` проверяет `src`, `tsconfig.node.json` проверяет конфиги Vite и ESLint. У них разные окружения и разные наборы типов, поэтому держать всё в одном файле неудобно. В `tsconfig.app.json` включены `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noUnusedLocals`, `noUnusedParameters` и остальные строгие флаги из предыдущего этапа.

**Почему CSS Modules.** В компонентах классы берутся через `styles["..."]`, поэтому имена не текут в глобальную область. Для такой мелочи хватает CSS Modules, отдельная CSS-in-JS библиотека тут не нужна.

**Почему ESLint и Prettier разделены.** ESLint ищет проблемы в коде, Prettier отвечает за пробелы и переносы. `eslint-config-prettier` отключает правила, которые спорят с форматтером.

**Почему проект должен запускаться на unix.** В скриптах нет виндовых команд, Prettier настроен на `endOfLine: "lf"`, версия Node.js зафиксирована. Git bash на винде я использовал как основной терминал.

## 2. Стейт-менеджер

**Выбран Zustand 5**

Почему не Redux Toolkit: для двух небольших сторов он тянет за собой больше кода и церемоний, чем пользы. Почему не Context: пришлось бы руками делать провайдеры, следить за лишними перерисовками и отдельно писать сохранение в `localStorage`. Zustand даёт маленький API, селекторы и middleware `persist`, который уже умеет то, что нужно. И без усложнений всё сложно.

В проекте два стора:

- **`authStore`** хранит `status`, `user` и `remembered`. Действия: `login` и `logout`. В `localStorage` через `partialize` попадает только `remembered`, поэтому статус и текущий пользователь не сохраняются.
- **`effectsStore`** хранит `isSnowing` и `easterEggMessage`. Действия: `toggleSnow` и `clearEasterEgg`.

Пара email и пароль в `localStorage` лежит в открытом виде. Это учебный проект, так делать нельзя. В реальном приложении пароль на клиенте не хранят, а для "запомнить меня" используют токен в `HttpOnly`-куке. Подробнее об этом писал в `native/README.md`, тут повторять не буду.

## 3. Компоненты

Самый приятный и адекватный этап работы

Интерфейс разбит по смыслу, а не один файл на всё

- **Каркас страницы:** `Header`, `Footer`, `Ticker`, `LoginCard`.
- **Блок соцсетей:** `SocialLogin` и `SocialButton`.
- **Форма:** `AuthForm`, `TextInput`, `Checkbox`, `SubmitButton`, `FormMessage`, `CardHeading`.
- **Эффекты:** `Confetti` и `Snow`.
- **Ссылки:** `FooterLink`.

`LoginCard` ничего не знает о валидации, он просто собирает два блока. `AuthForm` знает про поля и отправку, но не знает, как рисовать кнопку или сообщение. `TextInput` не знает, откуда берётся значение, он получает его пропсом и отдаёт изменения наверх. Так компоненты можно менять по отдельности и тестировать по отдельности.

Логика, которая не привязана к разметке, вынесена в хуки и модули:

- `useField` держит значение, состояние проверки и тряску одного поля;
- `useReducedMotion` подписывается на системную настройку через `useSyncExternalStore`;
- `useSecretCode` слушает последовательность клавиш;
- `validation.ts`, `auth.ts`, `classNames.ts` и `toCss.ts` остаются чистыми функциями без DOM.

## 4. ТестыЫ

Вот это просто ужас, тут хоть что-то уловить помогали гугл и нейронки.

**Что установлено:** Vitest 5.1.1, jsdom 31.0.1, `@testing-library/react` 16.3.3, `@testing-library/user-event` 14.6.13, `@testing-library/jest-dom` 8.0.0 и `@vitest/coverage-v8` 5.1.1.

**Почему Vitest.** Он использует тот же `vite.config.ts`, что и сборка, поэтому TypeScript, TSX и CSS Modules работают без отдельного преобразователя. API совместим с Jest, режим наблюдения быстрый. Для Jest пришлось бы отдельно настраивать ESM и TS, а смысла в этом при Vite нет.

**Почему Testing Library.** Тесты ищут элементы так же, как пользователь: по ролям, подписям и тексту, а не по внутренним классам и структуре компонентов. Если поменять разметку, но сохранить смысл, тесты не развалятся.

**Почему `user-event`.** Он ближе к реальному поведению: печатает по символам, кликает, переключает фокус и работает с клавиатурой. `fireEvent` тоже остался, но только там, где нужно вручную выстрелить событием, например `animationend`.

**Почему `jest-dom`.** Даёт читаемые матчеры вроде `toBeInTheDocument`, `toHaveClass`, `toHaveAttribute` и `toBeDisabled`. Без него пришлось бы вручную возиться с `classList` и атрибутами.

**Почему jsdom.** Нужны `document`, `localStorage`, `matchMedia` и события. В чистом Node.js этого нет. jsdom не идеален, но для компонентных тестов его хватает.

**Настройки в `vite.config.ts`:**

- окружение `jsdom`;
- `setupFiles` указывает на `src/test/setup.ts`;
- `fakeTimers.shouldAdvanceTime` включён, иначе `user-event` и фейковые таймеры зависают;
- `css.modules.classNameStrategy: "non-scoped"` нужен, чтобы в тестах были видны обычные имена классов, а не хеши;
- покрытие считается по `src/**/*.{ts,tsx}`, но без `main.tsx`, тестов и папки `src/test`.

**Что делает `setup.ts`:** подключает матчеры `jest-dom`, ставит заглушку `matchMedia`, размонтирует компоненты после каждого теста и восстанавливает моки. Ещё есть `polyfills.ts`: jsdom не умеет `AnimationEvent`, а React DOM проверяет его наличие при загрузке. Без полифила `onAnimationEnd` вешается на `webkitAnimationEnd`, и тест на окончание тряски не срабатывает.

## Ограничения

- Верная пара email и пароль захардкожена на клиенте. Это демо, никакой защиты тут нет.
- Пароль хранится в `localStorage` в открытом виде. В реальном проекте так нельзя, я писал об этом выше.
- Кнопки Google и Apple пока без логики. Это заглушки для интерфейса.
- Настоящего API нет, `requestLogin` имитирует задержку и ответ.
- Страница одна, роутинга нет. Для формы входа он и не нужен.
- Тесты компонентные и юнит, end-to-end сценариев в браузере нет.
